# 트러블슈팅 로그

증상 → 원인 → 해결 순으로, 시간순 누적 기록.

## 1. (Phase 2) RAG 검색 결과가 항상 빈 배열 — similarityThreshold 과다 설정

- **증상**: `QuestionAnswerAdvisor`를 조립했는데도 규정 질문에 "정보를 제공할 수 없습니다" 식
  거절 답변이 나오고, `RETRIEVED_DOCUMENTS`가 항상 빈 리스트.
- **원인**: `VectorStore.similaritySearch(threshold=0.0)`으로 직접 확인한 결과, 정답 청크의
  코사인 유사도 점수가 **0.487**인데 `application.yml`의 `day3.rag.threshold`가 **0.5**로
  설정돼 있어 전량 필터링됨. `text-embedding-3-small`의 한국어 짧은 질의-문서 쌍은 코사인
  유사도가 0.5를 잘 못 넘는 경우가 흔하다.
- **해결**: `application.yml`의 `day3.rag.threshold`를 `0.5 → 0.35`로 낮춤(`Day3Properties`가
  "실습에서 조정할 값을 코드가 아니라 설정으로 뺀다"고 명시한 튜닝 지점이라 완성 소스 코드를
  건드리는 게 아님). 재검증 결과 정답 청크(score 0.484)가 통과.
- **교훈**: RAG가 "검색 결과 없음"으로 보일 때는 프롬프트나 Advisor 순서를 의심하기 전에
  threshold를 실측(`similaritySearch(threshold=0.0)`으로 실제 점수 분포 확인)하는 게 빠르다.

## 2. (Phase 2) `bootRun`에 export한 `OPENAI_API_KEY`가 이어지지 않음

- **증상**: 첫 `bootRun` 실행 시 `OPENAI_API_KEY`를 export한 직후인데도
  "401: Incorrect API key provided: not-set" 에러로 RAG 인제스트 실패.
- **원인**: Bash 도구는 각 명령을 독립된 셸에서 실행한다(작업 디렉터리는 유지되지만 셸
  상태/환경변수는 유지되지 않음). `export`를 실행한 명령과 `bootRun`을 실행한 명령이
  서로 다른 호출이라 환경변수가 이어지지 않았다.
- **해결**: `export OPENAI_API_KEY=...`와 `./gradlew bootRun`을 **같은 Bash 호출(같은 명령)**
  안에 넣어 실행.

## 3. (Phase 2) `@SpringBootTest`에서 RAG 인제스트가 안 됨(첫 시도)

- **증상**: Advisor 체인 검증용 임시 테스트에서 `QuestionAnswerAdvisor`가 문서를 하나도
  찾지 못함(`RETRIEVED_DOCUMENTS` 빈 배열) — threshold를 낮추기 전 단계에서 확인.
- **원인**: `PolicyIngestService.ingestOnStartup()`은 `@EventListener(ApplicationReadyEvent.class)`로
  등록돼 있는데, `@SpringBootTest`는 실제 `SpringApplication.run()` 기동 경로와 이벤트 발행
  시점이 달라 자동 인제스트가 기대만큼 안정적으로 보장되지 않을 수 있다.
- **해결**: 검증 전용 임시 테스트에서 `policyIngestService.ingestOnStartup()`을 테스트 시작
  시 수동으로 한 번 호출. 실제 앱(`bootRun`)에서는 정상적으로 자동 인제스트된다(로그로 확인:
  "[RAG] 규정 문서 3건 → 청크 3건 인제스트 완료").

## 4. (Phase 3) `bootRun` 재기동 시 포트 충돌

- **증상**: TODO ⑦ 구현 후 `bootRun`을 재기동하려는데 `Port 8080 was already in use`로 기동 실패.
- **원인**: `pkill -f "gradlew bootRun"`으로 이전 프로세스를 내리려 했으나, 실제 실행 중인 프로세스는
  `java -jar .../gradle-wrapper.jar bootRun` 형태라 패턴에 걸리지 않아 살아있었음.
- **해결**: `lsof -ti:8080 | xargs kill -9`로 포트를 직접 점유한 프로세스를 찾아 종료.
  이후 재기동 전에는 항상 포트 기준으로 확인.

## 5. (Phase 2) Gradle이 코드 수정 후에도 `:test`를 UP-TO-DATE로 건너뜀

- **증상**: 테스트 파일을 수정했는데 `./gradlew test --tests '...'` 실행 결과가 이전 실행과
  동일(출력이 아예 없거나 이전 로그 재사용).
- **원인**: Gradle 데몬이 도중에 교체되면서(JVM 기준 불일치로 새 데몬 기동) 증분 빌드 캐시
  판단이 꼬여 실제로는 재컴파일이 필요한데 UP-TO-DATE로 판단해 건너뜀.
- **해결**: `--rerun-tasks` 플래그로 강제 재실행. 검증성 테스트를 반복 실행할 때는
  결과가 이상하게 안 바뀌면 우선 `--rerun-tasks`부터 의심.
