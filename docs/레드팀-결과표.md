## 뚫린 항목 요약 — 근본 원인 2가지로 수렴

1. **SafetyAdvisor 정규식이 좁다** (①⑤⑦ 공통 원인) — "지시 무시"류는 이전/앞선/기존 접두어에만
   반응하고, 주민등록번호는 7번째 자리 1~4만 커버한다. 매칭되지 않으면 **차단 없이 메모리(order 200)
   에 원문이 그대로 저장**돼, 이번처럼 모델이 우연히 거절해도 다음 대화 컨텍스트에 개인정보·인젝션
   문구가 남는다.
2. **실행 상한이 코드에 없다** (⑥⑧ 공통 원인) — `day3.tool.max-calls` 설정값이 선언만 되고 어디서도
   읽히지 않으며, 입력 길이 검사도 전무하다. 둘 다 "설정은 있는데 강제하는 코드가 없는" 동일한
   패턴이다.

Basic 인증 주체만 사용자 ID로 사용하고, 관리자 API는 미인증 401·일반 사용자 403을 반환한다.

## 소감

- **공격자로서 가장 쉽게 뚫었던 지점**: ⑥ 반복 유도. `max-calls` 설정이 선언은 됐지만 코드
  어디에도 연결돼 있지 않다는 걸 코드 리뷰에서 미리 확인했기 때문에, payload를 따로 궁리할 필요
  없이 "그냥 6번 시켜보면 된다"였다. 죽은 설정값이 가장 만만한 공격 표면이라는 걸 체감했다.
- **가장 인상 깊었던 발견**: ①⑤ 모두 **모델이 대신 거절해서 겉으로는 안전해 보였다는 점**.
  하지만 `GET /lab3/chat/history`로 대화 이력을 직접 열어보지 않았다면 SafetyAdvisor가 완전히
  우회됐다는 사실 자체를 놓쳤을 것이다 — "응답이 거절이니 안전하다"와 "코드가 실제로 막았다"는
  다른 이야기라는 걸 확인한 게 이번 레드팀의 가장 큰 소득이다.
