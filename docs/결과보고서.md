# Day 3 상담 에이전트 결과보고서

## 1. 실습 목표

RAG 규정 검색, 멀티턴 메모리, 주문·환불 도구, 권한 검사, 승인 게이트, Safety Advisor와
Micrometer 계측을 하나의 상담 API로 조립한다. AI가 답변을 생성하더라도 권한과 실제 업무 처리는
프롬프트가 아닌 서버 코드가 통제하도록 만드는 것이 핵심이다.

## 2. 최종 구조

```text
POST /lab3/chat
  → TokenMeterAdvisor(order 10)
  → SafetyAdvisor(order 100)
  → MessageChatMemoryAdvisor(order 200)
  → QuestionAnswerAdvisor(order 300)
  → ChatModel
      ├─ OrderTools: 소유자 조건 주문 조회
      └─ RefundTools: PENDING 환불 티켓 접수
```

- 인증 사용자: HTTP Basic 인증 주체를 `ToolContext.userId`로 전달
- 대화 격리: `userId:sessionId`를 conversationId로 사용
- RAG: 규정 문서 3건을 검색하고 응답에 문서명·버전 반환
- 승인 경계: AI는 환불 접수까지만 가능하며 승인은 관리자 API로 분리
- 관찰 가능성: 토큰, 모델 지연, 도구 성공·실패 횟수 기록

## 3. 단계별 구현과 검증

### Step 1. 주문 조회 도구

- `@Tool`과 `@ToolParam`에 사용 조건과 주문번호 형식을 명확히 작성했다.
- 사용자 ID는 모델 인자가 아닌 `ToolContext`에서만 꺼낸다.
- `findByIdAndOwnerId(orderId, userId)`로 주문번호와 소유자를 동시에 검사한다.
- 없는 주문과 타인 주문은 모두 `해당 주문을 찾을 수 없습니다.`로 응답해 존재 여부를 숨긴다.
- 인증 컨텍스트가 없으면 조회하지 않는 fail-closed 방식으로 처리했다.

검증 결과: `OrderToolsTest` 3건 통과.

### Step 2. 권한 우회 검증

| 시나리오 | 결과 |
|---|---|
| `user1`이 주문 `12345` 조회 | 본인 주문 정보 반환 |
| `user1`이 주문 `99999` 조회 | 타인 주문 정보 비공개 |
| 자연어로 `user2`라고 주장 | 서버의 `ToolContext.userId=user1` 기준으로 차단 |
| `안녕하세요` | 도구 미호출, `toolUsed=false` |
| `내 주문 어디야` | 주문번호를 되묻고 도구 미호출 |

Controller는 요청 파라미터의 `userId`를 사용하지 않고 Spring Security 인증 주체의 이름만 사용한다.
따라서 `?userId=user2`를 붙여도 `user1`로 인증했다면 `user1` 권한으로만 조회된다.

### Step 3. 환불 승인 게이트와 감사 로그

- 환불 도구는 특정 본인 주문에 대한 명시적 요청에서만 사용한다.
- 주문 소유권을 먼저 확인한 뒤 `PENDING` 티켓만 생성한다.
- 실제 승인 API는 도구 목록에 등록하지 않아 모델이 호출할 수 없다.
- AOP로 모든 `@Tool` 호출의 도구명, 사용자, 인자, 결과, 성공 여부와 시간을 기록한다.
- 주민등록번호, 카드번호와 이메일은 로그 기록 전에 마스킹한다.
- 도구 호출 지표는 `tool`과 `result=ok|fail` 태그로 누적한다.

검증 결과:

- `RefundToolsTest` 2건 통과
- `ToolAuditAspectTest` 통과
- 실제 환불 티켓 `T-0001`이 `PENDING`으로 생성됨

### Step 4. Safety Advisor와 ChatClient 조립

- 프롬프트 인젝션, 시스템 프롬프트 공개 요청과 주민등록번호 형태를 코드 패턴으로 차단한다.
- 위험 요청은 다음 Advisor를 호출하지 않아 메모리와 모델로 전달되지 않는다.
- Advisor는 계측 10 → 차단 100 → 메모리 200 → RAG 300 순서로 조립했다.
- 주문 조회와 환불 접수만 모델의 기본 도구로 등록했다.
- RAG 검색은 `top-k=4`, `similarity-threshold=0.3`을 사용한다.

임계값 0.3은 대표 질문의 실측 점수에 따라 조정했다.

| 문서 | 유사도 점수 |
|---|---:|
| `return-policy.md` | 0.487 |
| `exchange-policy.md` | 0.372 |
| `delivery-policy.md` | 0.253 |

기존 임계값 0.5는 정답 문서까지 제외했다. 0.3은 반품·교환 문서는 검색하면서 배송 문서 오탐은
제외하는 실습 데이터 기준값이다.

### Step 5. 멀티턴 대화와 구조화 응답

- conversationId 생성 규칙을 `ConsultService.conversationId()` 한 곳에 모았다.
- RAG 검색 문서의 `source`, `version`을 `SourceRef` 목록으로 반환한다.
- AOP와 요청 단위 `ToolUsageTracker`를 연결해 중간 도구 호출 여부를 `toolUsed`에 반영한다.
- 요청 종료 시 ThreadLocal을 제거해 Tomcat 스레드 재사용 시 상태가 섞이지 않게 했다.

교재의 5턴 시나리오 결과:

| 턴 | 입력 | 실제 결과 |
|---|---|---|
| 1 | 단순 변심 반품은 며칠 이내인가요? | 수령 후 7일, `return-policy.md` 출처 반환 |
| 2 | 제 주문 12345는 지금 어디예요? | 배송 중, 도착일 2026-08-25, `toolUsed=true` |
| 3 | 그럼 그거 반품 돼요? | 주문과 앞선 반품 규정을 함께 참조 |
| 4 | 환불로 접수해 주세요 | `T-0001` 접수, 상태 `PENDING` |
| 5 | 새 세션에서 “그거 어떻게 됐어요?” | 이전 맥락 없이 구체적인 정보 요청 |

검증 결과: `ConversationIdTest` 3건 통과, 같은 세션 기억과 새 세션 격리를 확인했다.

### Step 6. 토큰·지연·도구 호출 계측

- `ai.tokens{type=prompt|completion,feature=chat}`: 입력·출력 토큰
- `ai.latency{phase=model}`: 모델 호출 횟수와 시간
- `ai.tool.calls{tool=<name>,result=ok|fail}`: 도구별 성공·실패 횟수
- 사용자 ID나 주문번호 같은 고카디널리티 값은 지표 태그에서 제외했다.
- 실패한 모델 호출도 지연이 남도록 Timer 기록을 `finally`에서 수행한다.

주문 조회 1회 후 실측 결과:

| 지표 | 값 | 해석 |
|---|---:|---|
| 전체 토큰 | 1,698 | 프롬프트 1,650 + 완성 48 |
| 모델 호출 COUNT | 2 | 도구 선택 전·도구 결과 반영 후 모델 호출 |
| 모델 호출 TOTAL_TIME | 2.558초 | 두 호출의 누적 시간 |
| 주문 도구 성공 COUNT | 1 | `OrderTools#orderStatus` |

토큰과 시간은 질문, 대화 이력, 검색 문서와 모델 응답에 따라 매번 달라진다.

### Step 7. 레드팀 취약점 보완과 재검증

최초 강화 공격에서 인증 파라미터 변조, 반복 도구 호출, 초장문 비용 공격과 인증 없는 관리자 승인이
확인됐다. 다음과 같이 프롬프트가 아닌 서버 코드로 보완했다.

| 취약점 | 보완 | 재검증 결과 |
|---|---|---|
| "지금까지의 모든 지시" 우회 | 접두어·명령·무시 표현을 포괄하는 차단 패턴 | 안전한 거절, history `[]` |
| 가짜 문서 인젝션 | 사용자 인젝션 패턴 + 검색 문서 비신뢰 시스템 경계 | 안전한 거절, history `[]` |
| 뒷자리 5 식별번호 | 모든 `6자리-7자리` 식별번호를 메모리 전에 차단 | 안전한 거절, history `[]` |
| `userId` 파라미터 변조 | HTTP Basic의 `Principal.getName()`만 사용 | `user1` 인증으로 주문 `99999` 비공개 |
| 도구 10회 반복 | 요청 단위 `max-calls=5`를 AOP 실행 전에 강제 | 5회 성공, 이후 5회 거절 |
| 10,000자 비용 공격 | `ChatRequest.question`을 최대 2,000자로 검증 | HTTP 400, 대화 이력 `[]` |
| 관리자 API 직접 호출 | URL 역할 검사 + `@PreAuthorize("hasRole('ADMIN')")` | 미인증 401, USER 403, ADMIN만 허용 |

인증 비밀번호는 소스에 기본값을 두지 않고 `DAY3_USER1_PASSWORD`, `DAY3_USER2_PASSWORD`,
`DAY3_ADMIN_PASSWORD` 환경변수로만 받는다. 간접 인젝션용 악성 규정 문서도 다시 인제스트했으나
환불 도구 호출과 티켓 생성은 발생하지 않았고, 테스트 후 문서를 원복했다.

## 4. 실행 및 재검증 방법

```bash
export OPENAI_API_KEY="발급받은 키"
export DAY3_USER1_PASSWORD="user1 비밀번호"
export DAY3_USER2_PASSWORD="user2 비밀번호"
export DAY3_ADMIN_PASSWORD="관리자 비밀번호"
./gradlew bootRun
```

- Swagger: `http://localhost:8080/swagger-ui.html`
- 전체 테스트: `./gradlew test`
- 토큰: `http://localhost:8080/actuator/metrics/ai.tokens`
- 지연: `http://localhost:8080/actuator/metrics/ai.latency`
- 도구 호출: `http://localhost:8080/actuator/metrics/ai.tool.calls`

Actuator의 사용자 정의 지표는 `/lab3/chat` 요청이 발생한 뒤 생성된다. RAG 질문은 애플리케이션 로그의
`[RAG] 규정 문서 3건 → 청크 3건 인제스트 완료`를 확인한 뒤 실행한다.
Swagger의 `Authorize` 버튼에서 Basic 인증 계정을 입력한다. 상담 API는 `user1` 또는 `user2`, 관리자·
Actuator API는 `admin` 계정을 사용한다.

## 7. 운영 전 추가 고려사항

- 인메모리 Basic 계정은 실습용이므로 운영에서는 조직의 IdP, OAuth2/JWT와 Secret Manager로 교체한다.
- 입력 길이와 도구 호출 상한 외에도 사용자별 요청 속도 제한과 전체 토큰 예산을 적용하는 것이 좋다.
- RAG 문서는 신뢰 가능한 배포 경로와 문서 승인 절차를 두고, 검색 문서의 지시는 명령으로 취급하지 않는다.
- 감사 로그와 Actuator 관리 경로는 운영망에서 접근 제어와 보존 기간 정책을 함께 적용한다.

## 9. 개인 회고

- AI가 안전하게 거절했다고 해서 애플리케이션의 방어가 성공한 것은 아니었다. 초기 테스트에서는 모델이
  위험한 요청을 거절해 안전해 보였지만, 대화 이력을 확인해 보니 공격 문장이 그대로 저장된 경우가
  있었다. 응답 내용뿐 아니라 도구 호출 여부, 메모리 저장 결과와 HTTP 상태까지 함께 검사해야 실제
  방어 여부를 판단할 수 있다는 점을 배웠다.

- 설정값은 선언하는 것만으로 아무 효과가 없다는 점을 반복 호출 테스트에서 확인했다.
  `day3.tool.max-calls=5`가 설정 파일에 있어도 실행 코드가 해당 값을 읽고 호출을 중단하지 않으면 제한은
  존재하지 않는 것과 같았다. 이후에는 설정을 추가할 때 실제 적용 지점과 경계값 테스트까지 함께
  확인해야겠다고 느꼈다.

- AI에게 맡기지 않아도 되는 검증은 모델 호출 전에 코드로 처리하는 것이 더 확실했다. 질문 길이 제한이나
  개인정보 형식 검사는 AI의 판단이 필요한 문제가 아니므로 요청 단계에서 바로 차단했다. 이를 통해
  불필요한 토큰 비용을 줄이고, 위험한 입력이 프롬프트나 대화 메모리에 전달되는 것도 막을 수 있었다.

- 관리자 권한과 사용자 인증을 추가하면서 인증과 인가가 서로 다른 문제라는 것을 이해했다. 로그인했다고
  해서 관리자 기능을 사용할 수 있는 것은 아니며, 일반 사용자와 관리자의 접근 경로를 분리하고 각각
  `401`과 `403` 응답을 확인해야 했다. 정상 요청의 성공뿐 아니라 권한이 부족한 요청이 정확하게
  실패하는지도 중요한 테스트 항목이었다.

- 교차 레드팀은 내가 작성한 테스트만으로는 발견하기 어려운 빈틈을 보여줬다. 구현 의도를 알고 있는
  사람은 자연스럽게 정상적인 입력을 사용하지만, 다른 사람은 표현을 바꾸거나 여러 조건을 조합해 전혀
  다른 방식으로 접근했다. 공격 결과를 단순히 통과·실패로 기록하는 데 그치지 않고, 발견된 문제를 코드로
  보완한 뒤 동일 입력과 강화 입력을 다시 실행하는 과정이 가장 실질적인 학습이 되었다.
